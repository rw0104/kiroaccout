# Kiro 客户端隔离、多格式导出与当前请求适配

本轮承接第 4、5 项，并新增第 6 项：核验并更新登录、刷新和 AI 请求，改善稳定性。既有正式版为 1.7.6；涉及真实认证和跨 Windows 用户的行为尚需实机验收，新实现先按候选版本交付。

## 范围和验收

| 需求 | 本轮实现 | 验收条件 |
| --- | --- | --- |
| REQ-ISO-04 | Windows 独立用户下的 Kiro IDE 实例管理 | 不同本机普通用户 SID；用户配置目录已初始化；各自安装官方 Kiro；验证目标 EXE 数字签名和路径；通过系统 runas 加载目标用户配置，不保存密码 |
| REQ-EXP-05 | 完整备份 JSON、精简凭证 JSON、全部/选中、凭证开关 | 多提供商身份和区域往返一致；分组标签关系正确；不含凭证时删除 Token、密码及 clientSecret；空选择或失败不误报成功 |
| REQ-REQ-06 | 统一门户登录、刷新协调与当前 Kiro Runtime | 先取官方发行包证据；state/PKCE/会话和真实提供商绑定；单凭证单次并发刷新；验证有效响应及超时；区域正确，流帧校验和取消有效，消费型请求不盲目重放 |

## 隔离多开边界

官方当前仍有用户级认证缓存、系统凭据和协议。单独的安装目录、HOME 环境变量或 `--user-data-dir` 不能证明隔离。本轮使用操作系统独立用户身份，且每个 SID 仅配置一个实例；不复制管理器凭证、不调用全局切号或清除 SSO 缓存的旧接口。

用户预先在 Windows 设置中创建独立普通本地用户，登录一次，安装该用户自己的官方 Kiro。管理器枚举已初始化用户，排除当前 SID、系统账户和重叠配置目录；创建及启动前验证 EXE 位于目标用户配置目录且没有链接跳转，要求有效官方签名。点击启动时，系统 runas 窗口收取密码；不支持保存密码或把 PIN 当成密码。只展示“启动请求已提交”，不把启动器退出当成 IDE 已退出。

系统网络、机器级代理和证书仍共享，不宣称虚拟机级安全隔离。管理器不会创建 Windows 用户、复制生产账户、结束既有进程、删除用户目录，也不把本功能说成管理器 1.7.5/1.7.6 本身已经隔离。实机验收使用分别授权的独立账户，避免服务端刷新凭证互相影响。

## 当前请求依据

本轮固定分析官方 IDE 1.4.5 / Agent 1.1.499，来源、SHA-256、调用链和差异见[请求证据](../evidence/2026-10-20-current-kiro-requests.md)。统一门户采用 PKCE 与本地 HTTP 回调，Builder ID 使用已取证的 IdC 授权码链路；保留旧设备流为显式兼容方式。当前 Social 刷新与 AWS OIDC 刷新的核心字段没有证据表明需要改写，稳定性修复集中于合并并发、响应检查和受控失败。

AI 使用当前 Runtime 的实际 awsJson1_0 协议，不能仅根据 SDK schema HTTP trait 换 URL。按所选 profile/identity 区域构建目标；保留已取证的官方 provider 默认 profile，不猜测 Enterprise ARN。严格读取 AWS event stream，并阻止在已消费请求之后自动换端点或账户重放。官方还有服务功能配置控制的 Responses SSE 路径；本轮不在没有账户功能配置证据时默认启用。

## 必须保留的验收说明

离线测试、类型检查、编译和静态包检查分别记录。没有运行独立账户真实登录、跨用户 GUI 或真实 AI 请求时，不能写成已经完成实机验收。开发期间不启动生产客户端、安装器或真实自动更新，不读生产账户库、不刷新生产凭证，公开文件不包含本机私有目录和用户名。

本轮已完成 180 项离线回归、类型检查和源码构建。[官方客户端最小请求](../evidence/2026-10-20-official-client-smoke.md)经用户单独授权后通过；它只验证官方已登录客户端基线，不代替候选版新实现的真实调用验收。候选版打包和发布以对应工作流结果为准。

后续[新实现的真实 Runtime 请求](../evidence/2026-10-20-live-interface-checks.md)已返回 HTTP 200 并完整解析预期标记；仅当前 Social 会话得到局部验收。真实登录、刷新及跨用户多开仍待验证。

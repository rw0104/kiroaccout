# 1.8.0：单程序、多配置的 Kiro 客户端实例

用户确认的目标是：在同一 Windows 用户下，以一份官方 Kiro.exe 启动多个独立配置实例，并直接选择管理器内已有账户绑定启动。无需重复安装 Kiro、新建 Windows 用户或每次手动登录。本需求取代 1.7.7-rc.1 的独立 Windows 用户启动方案，历史记录保留，不自动执行或迁移旧配置。

正式发布目标为 Windows x64 **1.8.0**。发布前分别核实实现、离线测试、真实双实例和附件；没有证据的验收不得标记通过。

## 范围

| 编号 | 必须实现的行为 |
| --- | --- |
| INS-01 | 选择现有官方 Kiro.exe、实例名称和已有 accountId，生成唯一受管根目录；多个实例可使用同一安装 |
| INS-02 | 每个实例独立 user data、home、扩展、shared data、Agent 插件/数据及临时目录；初始化凭证只来自用户明确选择的管理账户，只读比较默认缓存防止共用凭证，不复制或改写默认缓存 |
| INS-03 | 只有同 Windows SID、同规范 EXE、精确实例参数、PID 与创建时间共同匹配的进程才属于该实例 |
| INS-04 | 启动等待真实主进程；恢复管理器后重新识别；不把启动器退出、残留 lock 或孤立 PID 当成存活证明 |
| INS-05 | 正常停止和重启按实例互斥；关闭超时保持运行，不自动强杀，不在旧实例尚存时启动第二份 |
| INS-06 | 进程自然退出后显示退出状态并允许手动重新启动，不把原因不明的退出谎报为崩溃，不自动反复拉起 |
| INS-07 | 运行中或归属未知时禁止移除配置；移除不递归删除用户数据，不结束既有进程 |
| INS-08 | 启停、失败和恢复一个实例不操作另一个实例或用户正在使用的默认 IDE |
| INS-09 | 管理器启动、退出和安装不声明或注销官方 kiro://；门户及 Google/GitHub 快捷登录使用本地 HTTP 回调 |
| INS-10 | 绑定期间实例独占该账户的刷新；管理器拒绝同账户刷新、切号和多绑定，防止服务端轮换竞争 |
| INS-11 | 正常移除须先停止并同步最新凭证；IDE 自行改登其他账户时，不能将其凭证写入原账户 |
| INS-12 | 无法核验缓存时提供显式确认的恢复解绑：仅确认停止后执行，先将原账户标记需重新授权，不回写未核验凭证、不删除任何实例文件 |

## 实现约束

路径由主进程根据 UUID 生成，不接受渲染层自由配置数据根。Windows 路径、标记、祖先目录和 reparse point 均须校验；不能通过链接跳转到生产目录。新实例不继承管理器的 KIRO_API_KEY、AWS 凭证或 VS Code/Electron 环境覆盖，父进程环境保持不变。初始化凭证只从用户明确选择的管理账户获取；启动前允许只读比较默认 IDE 缓存中的 access/refresh token，发现共用即拒绝，不复制或改写该缓存，也不为启动盲目刷新。过期 access token 可连同刷新凭证交给官方实例自行续期；无效刷新凭证、缺失或失效的 IdC 客户端登记需重新授权，不能虚构有效期。

accountId 与实例持久绑定，刷新归属不能只在窗口存活时内存记录。实例退出或管理器重启后仍须安全同步、验证同一账户并释放归属，不能使旧 Token 回写新凭证。多实例不能绑定同一管理账户；旧管理器或外部客户端不遵循本版绑定锁，文档必须说明不能并行消费同一份刷新凭证。高级空白实例可用于启动环境验证，但不能代替已有账户绑定流程验收。

默认创建必须明确选择已有账户；空白实例属于需显式选择的高级选项。若用户在 IDE 登出、改登其他账户，或新凭证到期后无法查询身份，正常移除不得绕过同步保护，也不能让账户永久困在绑定状态。恢复解绑需单独确认，仅允许确认已停止且没有残留子进程的绑定实例；重新授权标记成功后复核状态与路径，再移除配置。标记失败或状态不明时不解绑，不读取、覆盖或删除未核验缓存。后台同步与启停、移除、恢复解绑共用同一个实例操作锁。

官方 Windows User 安装包不支持强制 Portable，不能修改其 product.json 或补丁官方程序。只有经过检查且支持 Portable 的发行方式才可设置专用 Portable 根；其他安装使用明确目录参数。非 Portable 官方 GUI 可能重写 kiro:// 注册值，因此启动前必须确认已有处理命令指向同一官方 EXE；不匹配时拒绝启动，不能静默接管。外部 kiro:// 链接仍路由默认配置实例。

停止采用验证过进程句柄的正常窗口关闭请求。未保存文件导致等待时，应提示用户在目标窗口处理。禁止按进程名批量终止、只凭 PID 杀进程或自动强制退出。查询不完整、PID 复用、多个主进程或残留子进程无法归属时，显示“状态无法确认”并阻止危险操作。

旧 RC 的 Windows 用户配置仅显示停用状态，可移除配置，不读取其凭证、不启动其客户端、不删除其目录。账户管理器自身仍使用原有应用数据，不把此功能宣传成新旧管理器并存隔离。

| --- | --- | --- |

| 管理器重启恢复 | 新服务从复合身份恢复运行状态，拒绝 PID 复用 | 实机新建控制器从持久配置恢复两个运行实例；PID 复用拒绝有离线回归 |

| 两个真实账户 | 独立授权、实际缓存及刷新/回调归属 | 尚未取得，不作为空白实例测试的结论 |
| 已有账户绑定 | 两个不同 accountId 只写对应专用缓存；无重新扫码或全局切号 | 合成数据回归通过；双真实账户直接启动尚未验收 |
| 刷新归属与回收 | 拒绝同账户管理器刷新/切号/多绑定；停止后同步并释放；账号变化不串写 | 归属、缓存与轮换保护的离线回归通过；真实双账户轮换尚未验收 |

### 本轮实机记录

2026-10-20 会话中使用同一份官方 Windows Kiro **1.4.5**，在同一 SID 下并行启动两个不同受管根的空白实例 A、B。停止 A 后，B 的 PID、创建时间、EXE、所属 SID 和父进程均保持；重新启动 A 得到新主进程，B 仍保持。随后重建控制器，从持久配置重新识别两个运行实例；最后正常停止两者并确认退出。测试未使用真实账户，也未通过名称批量终止任何客户端。

该结果验证启动与生命周期，不证明已有账户的真实授权、Token 轮换或回调。1.4.13 的证据目前为静态核查，不能把 1.4.5 的 GUI 结果写成 1.4.13 实测。

同一轮另以 1.4.13 当前 ControlPlane wire 执行一次单会话只读身份查询，返回 HTTP 200 和非空用户 ID；没有刷新或写缓存。该结果验证身份查询，仍不代表 1.4.13 GUI 或双账户轮换通过。详细边界见[身份核验实测](../evidence/2026-10-20-kiro-instance-lifecycle.md#63-单会话只读请求结果)。本地离线回归最终为 273 项全部通过，Node/渲染层类型检查与生产构建通过；最终发布附件另由工作流校验。

## 隔离范围

这是正常使用下的配置和账户缓存分离，不是安全沙箱。同一 Windows 身份、DPAPI、系统网络、代理、证书和机器级资源仍共享。每个实例绑定不同账户；复制同一 refreshToken 给其他实例、旧管理器或外部客户端仍可能受服务端轮换影响。本版绑定锁不能约束不受其管理的其他程序。

多开启动及存储证据固定于 [Windows Kiro 1.4.13 / Agent 1.1.530](../evidence/2026-10-20-kiro-instance-lifecycle.md)。已有 AI Runtime 文本、工具事件和配置查询实测对应 [1.4.5 下当前 Social 会话](../evidence/2026-10-20-live-interface-checks.md)，不能扩大成 1.4.13 所有登录、刷新和请求协议均已验收。

## 1.8.1 修复记录

1.8.0 现场反馈的“安装路径必须手填、旧 OIDC 记录被误走登记校验、实例不能指定代理”已在 1.8.1 修复。安装发现使用只读进程/注册表/常见目录候选并逐个验证签名；导入兼容字段别名但仍拒绝未知 provider；实例代理仅作用于受管实例，停止后才能修改。后台同步不再改变生命周期状态 epoch，因此不会在正常轮询期间制造“状态刚刚变化”的假 unverified。

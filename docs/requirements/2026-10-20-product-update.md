## 2. REQ-UPD-01：软件内自动更新

应用启动后自动检查，并按受控间隔再次检查；用户可以在“关于”页面主动检查。默认使用本仓库稳定渠道，不从上游仓库下载，也不向稳定用户推送 RC。界面显示当前版本、可用版本和更新说明。

用户确认后下载，显示进度、速度或已下载大小。网络失败、无更新、下载失败和重试分别反馈，后台错误不得显示为“已是最新”。界面重新打开或订阅较晚时可查询主进程快照，不能只依赖一次性事件。

安装只能在有效更新已下载并通过更新器校验后，由用户明确确认触发。安装前确认账户数据保存成功；保存失败不得退出。禁止退出应用时悄悄安装，禁止无下载状态直接调用安装接口，禁止降级和重复并行下载。

| 验收编号 | 场景 | 通过条件 |
| --- | --- | --- |
| UPD-AC-01 | 启动与周期检查 | 使用 `rw0104/kiroaccout`，无并行检查风暴；退出清理定时器 |
| UPD-AC-02 | 稳定/RC 与版本比较 | 稳定用户不收到 RC；旧版本不被视为更新；RC 与正式版本比较正确 |
| UPD-AC-03 | 有新版本、无更新、请求失败 | 各状态可区分，版本与说明来自实际更新结果 |
| UPD-AC-04 | 下载、失败、重试 | 进度可见，可恢复失败，无重复下载或错误成功提示 |
| UPD-AC-05 | 安装前置检查 | 未下载或保存失败时拒绝安装；仅明确确认后重启安装 |
| UPD-AC-06 | 发布附件 | 正式版包含与安装器匹配的 `latest.yml` 和 blockmap；大小及摘要检查通过 |
| UPD-AC-07 | 测试边界 | 使用 mock 更新器验证状态机；不在生产 1.7.5 上执行真实更新 |

旧上游版本仍可能查询它原先的更新仓库。不能声称本仓库的新发布会自动把原版 1.7.5 切换过来；首次迁移和后续本仓库版本更新是不同流程。

## 3. REQ-PUB-02：README 与公开文档

README 以用户实际使用为中心，只保留产品用途、真实功能、下载、导入、更新和许可证入口。删除内部交接故事、私下开发环境叙述、未经验证的能力、广告和不适用的操作说明。

公开文档不包含本机绝对工作区、私人用户名、原始客户文件名、进程 ID、凭证和个人联系信息。技术文档采用仓库相对路径，必要的系统路径采用 `%APPDATA%` / `%USERPROFILE%` 等通用形式。本机运行资料留在 Git 忽略的本地目录，不再通过 README 的关联文档间接公开。

| 验收编号 | 场景 | 通过条件 |
| --- | --- | --- |
| PUB-AC-01 | 用户阅读 README | 功能与当前源码、页面和发布产物一致，不把待办当成已实现 |
| PUB-AC-02 | 当前公开文件扫描 | README 和关联文档没有本机绝对路径、私人用户名、原始样例文件名或进程标识 |
| PUB-AC-03 | 导航 | 本地文档链接存在；产品下载和源码入口指向本仓库 |
| PUB-AC-04 | 历史边界 | 不擅自改写 Git 历史；当前文件清理与历史提交仍可检索的情况分别说明 |

## 5. REQ-ISO-04：Kiro 客户端隔离多开（后续）

目标是在同一设备上管理并启动多个 Kiro 客户端实例，每个实例使用自己的环境和账户。这里的对象是 Kiro 客户端，不仅是账户管理器自身能开多个窗口。

后续设计需先核验当前官方客户端支持的参数与认证方式，再确定隔离边界。至少覆盖实例数据、浏览器/客户端会话、IDE 设置与扩展存储、工作区、凭证与刷新任务、进程与实例锁、端口、回调协议归属和生命周期清理；不能仅通过换目录或 `--user-data-dir` 声称全部隔离。

本地实例隔离不能改变服务端 Token 的有效性和轮换规则。验收使用分别授权的独立测试账户，不把同一份生产刷新凭证复制给多个实例并承诺彼此不受影响。

| 验收编号 | 场景 | 后续通过条件 |
| --- | --- | --- |
| ISO-AC-01 | 两个实例并行 | 均可启动，窗口与进程身份清晰，账户和设置互不覆盖 |
| ISO-AC-02 | 凭证与网络 | Token 刷新、缓存、端口和回调只归所属实例，不消费其他实例会话 |
| ISO-AC-03 | 启停与异常恢复 | 停止/重启/崩溃一个实例不结束或清理其他实例 |
| ISO-AC-04 | 既有资料 | 现有 1.7.5 与 Kiro 用户数据、生产协议及配置不被测试和新实例改写 |
| ISO-AC-05 | 可观察验证 | 使用独立测试账户检查文件、进程、回调和刷新隔离，未完成前不宣传已支持 |

## 6. REQ-EXP-05：JSON 导出（后续）

当前代码已提供 JSON 与 OIDC JSON 导出入口；本项记录用户要求的新增或完善方向，不把现有入口错误描述成完全不存在。后续先确认目标是增加格式、字段兼容、导出范围还是敏感字段控制，再实施。

设计应区分完整备份 JSON 和简化凭证 JSON，明确 `version/schema`、`provider`、`authMethod`、区域与必要凭证字段；覆盖全部/选中账户、分组标签关系和隐私选项。敏感字段开关须有明确规则，不能只清空部分 Token 却暗示整个导出已经脱敏。

| 验收编号 | 场景 | 后续通过条件 |
| --- | --- | --- |
| EXP-AC-01 | 完整备份往返 | 账户、分组和标签按定义恢复，格式版本可识别 |
| EXP-AC-02 | 简化凭证 JSON | Builder ID、Google、GitHub 等渠道保留可识别的身份、区域和必要字段 |
| EXP-AC-03 | 全部与选中 | 导出数量和范围符合用户选择，无静默遗漏 |
| EXP-AC-04 | 隐私选项 | 按明示规则移除 Token、clientSecret、密码等字段；不会误称含凭证文件为脱敏文件 |
| EXP-AC-05 | 文件与异常 | UTF-8、合法 JSON，取消或写入失败给出准确反馈，不误报成功 |

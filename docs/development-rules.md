# 修复期间的请求核验与环境隔离规范

日期：2026-10-19。适用规则见仓库根 [AGENTS.md](../AGENTS.md)。本文件约定后续修复的执行边界，不表示当前应用已经实现隔离启动。

## 1. 当前隔离状态

修复源码位于 `D:\kiroaccout\Kiro-account-manager`，用户的 1.7.5 安装位于 `D:\kiro-account-manager`。本轮只读取进程元数据、文件版本和路径，没有操作客户端、认证缓存或协议注册。

该次观测到主进程 PID 为 14256，文件版本为 1.7.5，userData 为 `C:\Users\reki\AppData\Roaming\kiro-account-manager`。PID 仅为当次观测记录，后续必须按可执行路径重新识别。

当前使用的隔离方式为：**独立源码目录 + 不启动开发客户端 + mock 的离线验证**。当前没有经过验证的 Electron 隔离运行模式，真实 GUI 和授权测试尚未进入。

已发现直接启动开发版会触及共享资源：

| 源码位置（相对应用目录） | 当前行为 | 必须处理的边界 |
| --- | --- | --- |
| `src/main/index.ts` 的 `app.whenReady` | 启动真实 Token watcher 并注册协议 | 启动前拦截，不可仅等 UI 禁用 |
| `src/main/kiroAuthSync.ts` | 缓存根来自 `os.homedir()/.aws/sso/cache` | 专用凭证根或禁用同步，不能仅切 userData |
| `src/main/index.ts` 的 `initStore` | electron-store 未指定独立 cwd | 在初始化前设置隔离 userData/存储根 |
| `src/main/index.ts` 的注册、退出处理 | 注册/注销共享 `kiro` scheme | 隔离模式禁止改生产协议 |
| `src/main/index.ts` 的窗口就绪逻辑 | 可从配置自动启动代理服务 | 禁用生产配置继承和自动服务启动 |
| `src/main/index.ts` 的 logout、switch、后台刷新与客户端配置 IPC | 可删除真实 SSO cache、修改 CLI 数据库、刷新账号或写入其他客户端配置 | 在主进程入口拒绝对生产资源执行，默认不连接生产账号 |

审计发现 logout 路径会遍历删除真实 SSO cache；不能为了“清理测试状态”调用该操作。隔离测试清理只能针对经过校验的 `.local/isolated/` 或测试临时根，不能从共享 HOME 推导删除目标。

## 2. 启动 Electron 前的必要条件

| 范围 | 必须满足的条件 |
| --- | --- |
| 应用数据 | userData、sessionData、账户库、备份、缓存、日志、下载与更新缓存都指向仓库 `.local/isolated/` 下的独立目录；不自动回退生产目录 |
| 初始化顺序 | 隔离配置在 requestSingleInstanceLock、store、watcher、日志初始化及其他副作用之前生效，检查模块级初始化 |
| 实例身份 | 独立实例锁和清晰的调试版身份；不能唤起/复用生产 1.7.5；退出只能处理本次启动的进程 |
| 凭证与数据 | 空白初始账户，仅合成数据或独立测试账户，不继承生产账号、refreshToken、cookies 或浏览器会话 |
| IDE/CLI | 默认禁用真实认证缓存读写、watcher、自动续期、账户切换、IDE/CLI 同步与机器码修改；需要测文件逻辑时使用临时根 |
| 系统操作 | 禁止协议注册/注销、系统代理与证书安装、开机启动、机器 ID 和其他共享系统状态写入；主进程入口提供保护 |
| 网络与端口 | 默认 mock；必要的本地 HTTP 服务只绑定 127.0.0.1，用动态或事先确认未占用的专用端口；不探测生产代理来调用真实账号 |
| 更新与安装 | 禁用自动检查/下载/安装和退出时更新；打包不等于安装，不运行会覆盖现有版的安装器 |
| 浏览器授权 | 使用隔离浏览器会话/独立 OS 环境及测试账户；保留 state/PKCE 和 provider 校验，不为绕过协议归属而放宽验证 |
| 验证证据 | 启动前后记录生产主进程路径、版本和共享资源未被开发测试写入的证据；不以路径配置存在代替实际文件访问和系统操作验证 |

在当前用户的 Windows 会话内，Social 自定义协议回调与生产 `kiro://` 可能冲突。先以 mock 驱动真实回调处理代码；真实外部协议交接放到独立 OS 用户/虚拟机，除非已有经验证且上游允许的隔离回调方案。

## 3. 最新请求证据应怎样记录

每次修复受影响的 Kiro 请求链路，在对应分析文档中记录：

- 获取日期、官方来源 URL/提交或客户端安装包来源、客户端/CLI/SDK 版本；区分“官方最新版”和“当前机器安装版”。
- 测试渠道、区域、认证方式、端点、method、header/body 字段名称及结构。
- 设备授权间隔、slow_down、state/PKCE、redirect URI、Token 有效期和轮换等与问题有关的协议要求。
- 与 1.7.5 实现的具体差异、最小脱敏请求/响应观察、错误码与复现步骤。
- 哪部分由当前实现/官方文档支持，哪部分经隔离实测确认，哪部分仍未验证。

本轮已有的历史分析是 1.7.5 的缺陷基线，不构成“最新 Kiro 协议已获取”的证明。后续修复不要将旧文档中的固定字段直接升级为新的事实。取证不改变当前运行的 1.7.5，不对其账户刷新 Token。

## 4. 安全的当前工作顺序

1. 只读复核用户版与修复源码版本、生产进程和安装路径。
2. 根据待修链路获取当前官方请求依据；需要真实请求时在独立环境使用测试账户取证。
3. 离线复现本地解析与登录会话问题，保存脱敏证据。
4. 修复独立可验证的代码，执行类型检查、回归和构建。
5. 完成第 2 节隔离条件后，才进入开发客户端/打包 GUI 和真实授权验收。
6. 交付时记录结果及未验项目，保持生产 1.7.5 的安装、数据和运行状态不被测试改动。
